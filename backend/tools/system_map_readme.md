# Backend system map

This README is generated from `tools/system_map_readme.md`; edit that source and run `--write`.

Generated by `tools/system_map.py` from Go source (`go list -deps -export` + `go/types`),
`CANONICAL_TABLE_OWNERSHIP.json`, `I9_MODE_SURFACE_V1.json`, `tools/missions_content.py`,
the virtual-client scenarios, and two committed inputs: `client_mid_callers.json` and
(when a suite has run) `scenario_coverage.json`. Do not edit generated files by hand.

## Read only what the question needs
- `show <mid>` gives the registered owner and client references; `show <system>` gives its record and both edge directions. Both also join the popup rows of that MID or system from `docs/architecture/popup_catalog/POPUP_CATALOG.json` (see `tools/popup_catalog_readme.md`).
- `calls[A][B]` means **A calls B**; `called_by[A][B]` means **B calls A**. Edges are direct static call sites, not a request's full dependency list.
- `trace <mid>` walks a bounded static route with source references. Keep `FANOUT`, `UNRESOLVED` and `BOUND` markers; check source before treating a possibility as fact.
- `show unhandled` lists client-sent MIDs without an owned, concrete handler. Window file references are not proof of runtime reachability; dead code is not inferred.
- Lock rows are static candidates and can be incomplete across wide interfaces or adapter-owned paths. Use a route trace for request-specific locks; neither view proves execution or lock order.
- Contract matches and scenario names are reading leads. Check source and accepted PassMap contracts before changing behaviour; use runtime evidence for deployment, active content and executed-test claims.

## Files
- `INDEX.json` – one row per `internal/application/<system>` with counts and purpose,
  plus `mid_to_system` and `table_to_system`.
- `EDGES.json` – `calls`, `called_by`, `composition` for every system.
- `systems/<system>.json` – one system; `show <system>` joins its edge detail without reading all of `EDGES.json`.
- `FINDINGS.json` – review leads, not verdicts. `client_senders_without_live_handler` lists every MID with a same-line client `request(` sender but no owned, concrete handler; `unattributed_pushes` retains registrations whose owner cannot be resolved.
- `client_mid_callers.json` – MIDs, names, files, `senders` (same-line `request(`), `other`. A sender is a static source reference, not proof the file is loaded or reached at runtime.

## Fields
- `mids` – registered stock HTTP MIDs, client names, and the handler `file:line`
  (the dispatcher's `Dispatch` method); dispatcher files once per system. Registration
  does not imply positive gameplay support: a route can deliberately refuse a legacy MID.
- `MID_CLASSES.json` – C1-3a static class of every registered stock HTTP MID; `show <mid>`
  prints one row. `isolation`, `read_only` and `retry` list every `Runner.Run` the route
  reaches, with the call site `file:line`. `writes` is `state` (write SQL other than the
  receipt store itself), `receipt` (the route records an operation receipt and writes no
  other state), `none`, or `UNKNOWN`. `unbounded_read` lists read SQL with no `LIMIT` and no player/actor key in
  its `WHERE`. A `FANOUT`, `UNRESOLVED` or `BOUND` marker is kept in `unknown`; when one
  could hide a write the class stays `UNKNOWN`, never a guess. Inactive fallback
  registrations have no route and are `UNKNOWN` with that reason.
- `pushes` – realtime S2C registrations attributable to the system.
- `tables.owned` – tables whose ownership `owner` names this system.
- `tables.read` / `tables.written` – tables in the SQL of this system's own package and of the
  store methods it actually reaches, function by function. The walk stops at another application
  system, whose tables are its own (see `calls`), and at an interface with more than three
  implementers, so treat them as a lower bound where a `FANOUT` applies. `content` is the
  `content_*` read subset.
- `stores` – the postgres store packages those typed edges reach.
- `calls` / `called_by` (in `EDGES.json`) – direct static call sites grouped by system, with inverse caller lookup. A leading
  `*` marks a call through an interface (`via_port`). Wide interfaces (more than
  `implementerThreshold = 6` implementers) appear as `interface:<pkg>.<Name>`.
  A store target is `store:<package>` unless `<x>store` names an application system `<x>`;
  `i4store`, `kernelstore`, `contentstore` and similar stay explicit store targets.
- `composition` (in `EDGES.json`) – dispatcher/service construction files attributed by
  the registration walker; these can differ from the file that registers the MID.
- `contracts` – documents mentioning the system's MID numbers or touched table names,
  matched lexically. A match is a reading lead, not a selected contract or proof of
  applicability. It can include historical versions and miss a new stage contract
  until that contract is published into `docs/i9`; consult the PassMap registry and
  the active stage's contracts before changing behaviour.
- `decorated_by` – registration wrappers such as `observing`.
- `facts` – `emits` resolved through `go/types` constants (simple same-function assignments
  followed); `consumers` maps each emitted fact to mission task kinds, high-water kinds,
  entitlements and Adventure events; `reads` for mission/Adventure owners.
  Unresolved kinds are listed in `FINDINGS.json` `gaps`.
- `login` – MID 1 / lobby contributors and overlay functions attributable to one system.
  `INDEX.json` `login_composition` is the literal contributor list in composition order, including
  store adapters and local variables that no single system owns; start there for "who builds login".
- `background` – `runReconcile` loops (gxb-api) and River enqueues/workers.
- `locks.ranks` / `locks.profiles` – referenced `*LockRank` constants and tx `LockTimeout`.
  `locks.row_locks` and `locks.row_lock_methods` – PostgreSQL lock clauses found in stores and
  attributed through typed application-to-store edges plus a bounded store-local caller walk.
  These are lower-bound static candidates: wide interfaces and adapter-owned request paths can
  hide callers, and call arguments can disable a conditional clause. Use `trace <mid>` for the
  route-specific static walk; neither view proves execution or complete lock order.
  `locks.unresolved_methods` names lock clauses whose table cannot be resolved locally,
  such as a suffix passed to another function; an empty table name is never invented.
- `tests.scenarios_naming` – scenarios that name a MID in text; not coverage.

## Commands
```
python3 tools/system_map.py --write
python3 tools/system_map.py --check
python3 tools/system_map.py show <system|mid|table|unhandled>
python3 tools/system_map.py trace <mid> [--full]
python3 tools/system_map.py --refresh-client <src_64>
python3 tools/system_map.py --refresh-coverage <one-mid-per-line-file>
```

The hooks in `tools/githooks` run `--write` and stage the result in every commit and merge commit; turn them on once per repo with `git config core.hooksPath tools/githooks`. `--check` in `tools/check.sh` is the backstop. If a merge conflicts inside the map, resolve it by running `--write`.
`--check` fails on stale generated files, validates every generated path exists, checks the
campaign/clientlog attribution anchors, and re-runs bounded `trace` checks for MIDs 114, 161, 338 and 528,
plus negative sibling-route checks for Achievement MIDs 1302/1303.
Trace assertions match symbols, source paths and required tables; source line numbers
remain navigation metadata and may move without changing a relationship.
`show missions` aliases to `i5`: there is no `internal/application/missions` package.
Type-check errors stop generation before files are written; they cannot silently replace
the last good map with a partial package analysis. Client/coverage refreshes remain explicit.

## trace versus show
`show <system>` joins the generated, committed view: attribution, tables, stores, composition and
cross-system call names. `trace <mid>` is computed live and is the right tool for "what does this
request potentially touch": a system's own table list is not the complete cross-owner write set.
Recognised MID switches and equality/inequality branches are pruned; other conditions
remain conservative possibilities. From the registered dispatcher it follows these branches, then the
function-level call graph (each function once), printing `file:line`, SQL tables with read,
write and `FOR UPDATE`/`FOR SHARE` (`conditional lock` when a branch appends the clause, so the
caller's argument decides), objective fact kinds recorded, and push calls. A repeated function that
touches tables prints `(seen above, touches tables)`.

By default, `trace <mid>` compacts the shared `HeroDispatcher.actor` to
`RealtimeAuthority.ResolveGameplayBearer` authentication walk to one summary and its SQL line.
It drops non-application leaf calls with no children, limits each `FANOUT` to five names plus
`... (+N more)`, and groups unresolved local function values (`cancel`, `release`, `body`,
`acqCancel`, `txCancel`, `reconcileCancel`) into one count per frame. Application calls, every
`sql:` line and lock clause, and all `FANOUT`, `UNRESOLVED`, and `BOUND` markers remain visible.
Use `trace <mid> --full` for the original unabridged output.
Registered wrappers that are not traversed are named in an `UNRESOLVED registered wrapper`
line: the inner dispatcher walk omits their effects. SQL relation extraction remains lexical;
it handles common CTE aliases and joins but is not a full PostgreSQL parser.

## Limits
- Interfaces declared outside this module (including the universe `error`) and anonymous
  interfaces whose methods are only error inspection (`SQLState`, `Unwrap`, `Is`, `As`,
  `String`) are ignored when resolving ports.
- Interface implementers are searched among package-level named concrete types, including
  unexported types, in `internal/application` and `internal/adapters/postgres`.
  Local unnamed types and implementations outside those directories are not resolved.
- Fact kinds assigned through non-constant expressions are reported in `gaps`.
- `FINDINGS.client_senders_without_live_handler` uses `client_mid_callers.json` same-line `request(` matches and current registrations. `window_sender_files` is source-path evidence only; runtime reachability and dead-code status remain unknown. Registration status separates absent, fallback-only, unattributed and handler-less registrations.
- `FINDINGS.soft_refusals` finds literal refusal bodies only and does not state the HTTP status;
  it misses a 200 that replays a stored or duplicate result (for example 30005, 30002). A review lead.
- Locks are candidates, never a proven order; clauses reachable only through wide interfaces or adapter-owned routes may be absent from a system row. SQL text without `FOR UPDATE`/`FOR SHARE` (e.g. `pgx.CopyFrom`) is not a row lock here.
