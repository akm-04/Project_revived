PHASE B — REAL POSTGRESQL 18.6 CA1 HARNESS
-------------------------------------------
Use a real PostgreSQL 18.6 instance. SQLite/mocks are not evidence for this phase. Apply the exact canonical migrations through 00013 using the repository's qualified migration workflow. Record DB version, migration history and schema hash/checks.

CA1 deliberately has no production Character tables/provider. Build the real-DB test fixture outside release source, or in an isolated test-only copy/harness. The fixture must:
- implement `PartnerEntityMaterializer` using real PostgreSQL rows solely for test evidence;
- expose a deterministic per-player Character namespace/instance table in a TEST schema or temporary schema;
- lock exactly provider-declared 400–599 keys;
- enforce unique `(grant_semantic_key,line_ordinal)` identity in the fixture so duplicate materialization is observable;
- never alter release migrations or production schema;
- use the caller's exact transaction;
- permit forced late errors for rollback tests.

Required real-DB cases:

B1. MIXED ATOMIC SETTLEMENT
- One semantic Grant with PartnerEntity + scalar + stack.
- Verify one Character fixture instance/materialization, exact scalar/stack effect and one Grant receipt in the same transaction.
- Verify receipt schema v3 and typed payload.
- Reconnect/new pool and replay: exact original typed result; no second instance/economic settlement.

B2. SAME-SEMANTIC CONCURRENCY
- At least two concurrent sessions issue the same semantic mixed entity Grant.
- Force overlap around Character/I5 locks.
- Expected: one committed materialization/economic settlement; other call converges by replay or qualified SERIALIZABLE retry/reconciliation; no duplicate entity; no blind retry after unknown commit.

B3. LATE PROVIDER FAILURE ROLLBACK
- Provider fixture acquires declared locks, mutates its fixture row, then returns a forced error before Grant receipt completion.
- Verify entire transaction rolls back: no fixture row, no scalar/stack change, no Grant receipt.

B4. AGGREGATE PREFLIGHT/CAPACITY FAILURE
- Provider preflight rejects a multi-line batch as a unit.
- Verify no Character/I5 mutation and no receipt.

B5. UNDECLARED/INVALID LOCK DEFENSE
- Fixture attempts/returns a key outside 400–599: planner must reject before mutation.
- If feasible, instrument fixture to demonstrate that CA1 never asks it to lock an undeclared key.

B6. REDEEM LOCK-ORDER REPRODUCER (MANDATORY)
Construct the exact same-player contention pattern that motivated CA1-R0:
- T1: MID230/Redeem path with progression eligibility plus a reward requiring Economy and preferably a test PartnerEntity as well.
- T2: ordinary Grant requiring Economy + Progression (e.g. a mixed scalar/PlayerExp plan qualified by current content fixture).
- Synchronize/barrier the sessions so old Pass509 ordering would be capable of 710->700 versus 700->710 conflict.
- On the CA1 candidate verify the lock acquisition order is lower-to-higher and the run converges without a PostgreSQL deadlock.
- Run enough repetitions to make scheduling evidence meaningful; record SQLSTATE/retry counts. Serialization abort/retry may be valid; deadlock from inverted owner order is not.

If practical, run the same harness against untouched Pass509 only as differential evidence to demonstrate the old call ordering/deadlock opportunity. Do NOT require the historical baseline to deadlock deterministically to prove the static inversion.

B7. MATERIAL DEBIT
Using real I5 rows in one caller-owned transaction:
- scalar + multiple stacks;
- shortage in final resource => no persistent writes after rollback;
- stack exactly to zero => row deleted according to accepted semantics;
- imported over-cap stack can spend down;
- concurrent debit of same player/resource set converges without negative balance.

B8. DIFFERENT-PLAYER INDEPENDENCE
Concurrent entity/material debit on different players should not share the same Character/I5 owner locks unnecessarily.
