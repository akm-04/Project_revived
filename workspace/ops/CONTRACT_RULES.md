PORTABLE CONTRACT REGISTRY AND CONTRACT MANIFESTS (direct user instruction, 2026-11-10)

Contracts are the foundation of the project, so binding contracts reach every worker mechanically, not through anyone's memory, the lead's included.
- Each stage owns one portable registry at `work/<phase>/stages/<stage>/REGISTRY` (`ops/contract_registry.py`). It is the authoritative working contract registry for the stage: opened once from the latest seal (sealed registry, phase inputs and the stage's `contracts/` folder, JSON and Markdown), changed only by explicit lead actions (`add` for a new or amended contract, `accept` after reviewing an absorbed one, `bind` to place a contract on systems, `bind-path` to own changed files the map cannot place, `waive` for a recorded exception, `integration` for the stage's integration worktree and base commit), and exported into `passmap/inputs` at stage close. Every change bumps `revision`, appends to `history.jsonl` and replaces the JSON files atomically. Documents are stored content-addressed under `documents/<id>/<sha256 prefix>-<name>` and never overwritten, so every pinned manifest path stays readable and two contracts with the same file name never collide. The next stage opens a fresh copy from the new seal, inheriting the lead's system and path bindings.
- A contract's identity is the id its document declares: `contract_id` or `policy_id` in JSON, a `Contract-Id: <id>` line in Markdown (a Markdown file named after a registered contract is that contract). A file name never establishes identity. A new Markdown contract without a `Contract-Id:` line is research, not a contract, and is not absorbed. `check` reports an UNREGISTERED id, a DIVERGED copy (legacy aliases included), a DUPLICATE id with two contents in one folder, a shared or missing document and an altered registry copy. It also sweeps the whole backend `docs/` tree and the sealed `hot/00_PASSMAP` recursively: a document that declares an id or is named like a contract, policy, decision, amendment, authorization or implementation-notes record must be registered (by content, id or name) or classified by the lead with `classify <stage> <docs|hot>/<path> --reason <why>` into `REGISTRY/not_contracts.json`; otherwise it is UNCLASSIFIED and the check and seal-check fail. A contract found late is registered with `add --origin-stage --origin-phase --origin-commit --note` so its export keeps the stage that made it.
- Compliance is recorded, not assumed (user, 2026-11-10). `contract_manifest.py matrix` generates `REGISTRY/COMPLIANCE_MATRIX.json` (every contract's revision, origin, systems, MIDs, production paths, test files and per-system verdicts) and prints the counts. Audit verdicts enter only through `contract_manifest.py record-verdicts FILE --by POOL [--reviewed]`, pinned per system to the contract's sha256: UPHELD needs file:line evidence and a test that asserts the clause and passed (existing code or a passing package is not compliance), an amended contract's verdicts turn STALE, and a contract counts as verified upheld only when every bound system is UPHELD and lead-reviewed. seal-check refuses a current PARTIAL or VIOLATED finding until a re-audit or a waiver. The bypass proof is `SealCheckTests`: merges made with `--no-verify` are still refused at the seal. Recovery record: work/i9/stages/I9-11/contract_recovery/RECOVERY.md.
- The registry and the system map stay separate: the registry says which rules bind, the map (generated from code) says what exists. `ops/contract_manifest.py` joins them deterministically in both directions (`system <name>`, `contract <id>`): a contract binds a system when its document names the system's MIDs (every member of a JSON `mids` array or any key ending in mid/mids, every MID of a prose list or range such as `MID 32/33`, `MIDs 560-571`, `MID64`, but not a requirement label such as `MID-01:`) or MID names, owned tables or package path, when the contract id names the system, when the system's source cites the contract id, or when the lead bound it. A live contract that nothing places is an unresolved coverage issue: `coverage` lists it in `REGISTRY/COVERAGE.md`, every manifest counts it, and it blocks every merge and seal until the lead binds it to systems, to all (`--global`) or to no code (`--no-code`).
- Every queued task starts with `Contract-Systems: <system>, ...` (or `Contract-Systems: none - <why>`; a system the task creates is written `<name> (new)`), for a worktree `Contract-Tree: <dir>`, and optionally `Contract-Ids: <id>, ...` for contracts the lead names on top of the lookup (always for a new system, which the map cannot place yet). `ops/fleet_queue.py` refuses a prompt without the systems line, with an unknown system or with an unregistered id. For a system task it builds the manifest (ids, status, why each applies, document paths, sha256) from the registry and that tree's map, puts it above the task text, pins it in `NN-name.manifest.json` with the registry revision and the tree's HEAD, and after the answer checks the worker's `## Contract compliance` section: a row per manifest contract (APPLIED with an existing non-test file:line and the test that proves it, as an existing `_test.go` file:line or a `TestXxx` function the tree defines; NOT_APPLICABLE with a reason; or CONFLICT), and a transcript read of every APPLIED or CONFLICT document. One corrective follow-up is sent; a task that still fails or reports a CONFLICT stops the queue for the lead, printing the CONFLICT rows. Every outcome is appended to `REGISTRY/dispatches.jsonl` with the commit it was checked at.
- The merge check (`ops/contract_manifest.py merge-check --tree <leaf> --base <branch point> [--revalidation-queue <queue>]`) fails closed. `--dry-run` previews without absorbing; a real check absorbs, so run it only on the leaf being merged. `--into <ref>` (repeatable) names refs already merged into the integration branch; files their commits changed are not charged to the leaf. The I9-11 leaves share history (criss-cross merge bases), so pass each earlier-merged leaf (or the integration HEAD, which the merge hook does itself). It absorbs the leaf's committed contract documents (read from git, never the working copy; review pending; a document changed by both the leaf and the registry since the branch point is a CONFLICT, two documents declaring one id a DUPLICATE, and nothing is saved unless every document was handled), then fails on: any REVIEW_PENDING contract, any unplaced contract (COVERAGE), a binding to a system the map lacks (STALE_BINDING), a changed file no system owns and no path binding covers (UNMAPPED), a changed system without a manifest task checked at a commit in the branch's history (UNCOVERED), code changed after that task (CHANGED_AFTER_CHECK), no passing task from a pool other than the ones whose Co-Authored-By trailers wrote it (INDEPENDENT_AUDIT; Luna audits DeepSeek work and the reverse; lead-written work may be audited by either), a latest task that did not pass (COMPLIANCE), or a contract amended or added since the task's pin (REVALIDATE, which also writes a revalidation task into the named queue). A lead's own fix to a leaf counts only after a manifest task on it passes.
- Enforcement does not depend on anyone running the check. The stage's integration worktree (recorded with `contract_registry.py integration`) runs it on every merge commit through the backend hooks `tools/githooks/pre-merge-commit` (clean merges) and `pre-commit` (conflicted merges), and refuses the commit on a failure. Merge one leaf at a time with `--no-ff`; never pass `--no-verify`. `ops/seal_passmap.sh` runs `contract_manifest.py seal-check` before anything else: the registry check against the stage folder and the canonical backend docs, the merge check of everything the canonical backend changed since the stage's base commit (which also catches a fast-forward or a bypassed hook), and the export. A seal cannot proceed while any applicable contract is missing, stale, unreviewed or unaccounted for.
- The lead's only way past a problem is a recorded, reviewable exception: `contract_registry.py waive <stage> "<KIND> <subject>" --reason <why>` (for example `STALE_BINDING I9_11D_COMPAT_V1` until the leaf that creates the system merges). Every later check prints the problem as WAIVED with the reason, and the stage handoff lists the waivers. A waiver never replaces `accept`, `bind` or `bind-path` where those settle the problem.
- The tools carry regression tests: `cd ops && ../.toolchain/bin/python3 -B -m unittest test_contract_workflow` plants each known defect (a basename hiding a new id, an alias divergence, colliding file names, a dirty working copy, a missing MID in an array, a test file cited as code, a clean merge before MERGE_HEAD exists, a nested unclassified document, a stale classification, and every merge-check failure kind) and must stay green after any change to `ops/contract_*.py`, together with each tool's `--check`.
- A worker's compliance table is a claim like the rest of its report: the lead still reads the diff and checks cited lines, and acceptance still comes from the gates.
